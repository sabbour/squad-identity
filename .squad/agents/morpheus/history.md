# Project Context

- **Owner:** Ahmed Sabbour
- **Project:** squad-identity — GitHub App bot-identity governance for Squad agents. Ensures every agent-authored GitHub write (PR, comment, label, push, commit) uses the correct `{app-slug}[bot]` identity rather than the human operator's personal `gh` token.
- **Stack:** Node.js (built-ins only — no npm dependencies), GitHub Apps API + JWT, `gh` CLI, Squad plugin architecture (extension + skill + scripts)
- **Architecture:** Three layers, all upgrade-proof:
  1. **Extension** at `.github/extensions/squad-identity/extension.mjs` — registers 5 Copilot CLI tools (`identity_status`, `identity_doctor`, `identity_update_charters`, `identity_update_copilot_instructions`, `identity_setup_steps`) and on `onSessionStart` syncs `lib/*.mjs` → `.squad/scripts/`.
  2. **Skill** at `.squad/skills/squad-identity/SKILL.md` — protocol agents read at spawn; Steps A–D (env, token capture, inline use, post-flight) and anti-patterns.
  3. **Scripts** at `.squad/scripts/` — the runtime callable scripts (`resolve-token.mjs`, `post-flight-check.mjs`, etc.).
- **Created:** 2026-04-28

## Learnings

- **2026-04-29 (final):** GitHub App PEM keys are **owned by the app creator, never transmitted to installers.** Public GitHub Apps from the marketplace give installers only `installation_id` + `client_id` — not the PEM. Without the PEM, the JWT-signing step of the GitHub App token exchange protocol fails. Shared public apps (`sqd-*`) therefore do not work as an end-user authentication model unless a central token broker is built. Custom apps (`{alias}-sqd-{role}[bot]`) are the only **working** path: user creates the app, holds the PEM in their keychain, owns the lifecycle. This reshapes app tier prioritization: custom is primary (today), shared is future/conditional (if broker arrives). Decision recorded in `.squad/decisions/inbox/morpheus-reframe-app-tiers.md`.

- **2026-04-28 (final):** Three-iteration arc converged on npm-wrapped extension: plugin (no) → extension (yes) → npm distribution (final). Future architecture decisions should check Squad's own conventions FIRST before exploring novel patterns. The `@bradygaster/squad-cli` precedent gave us the shape for free; `@sabbour/squad-identity` follows it directly. npm + postinstall hook is the distribution substrate — no net cost, semver lifecycle built-in, same mental model as Squad users already know.

- **2026-04-28 (final):** The Copilot CLI plugin system (agent/skill/hook/MCP support) and the extension SDK (`@github/copilot-sdk/extension` + `joinSession`) are two distinct mechanisms. **Do NOT conflate them.** Plugins use `plugin.json` manifests and have native install/update/uninstall lifecycle; extensions use `.mjs` files on disk and have no install command. The "unicorn" option (plugin wrapping an extension) is not supported — `plugin.json` has no `extensions` field. For squad-identity, the extension SDK is the right fit because the 5 tools + onSessionStart hook already work; plugin conversion would require a full MCP server rewrite for zero behavioral gain.

- **2026-04-28 (refined):** Two install forms exist and are NOT mutually exclusive — both work with the same `plugin.json`: (1) `copilot plugin install PLUGIN-NAME@MARKETPLACE-NAME` resolves via a registered marketplace repo; (2) `copilot plugin install OWNER/REPO` clones directly. Shipping a valid `plugin.json` (valid locations: `.plugin/`, `.github/plugin/`, `.claude-plugin/`, or repo root) enables both for free. The marketplace form is the preferred UX; direct-from-repo is the zero-registration fallback. A marketplace is itself a repo with a manifest listing plugins; users register it with `copilot plugin marketplace add OWNER/REPO`. Default marketplaces: `copilot-plugins`, `awesome-copilot`.
- **2026-04-28 (refined):** The plugin system does NOT support the extension SDK (`@github/copilot-sdk/extension` / `joinSession`). `extension.mjs` must be reimplemented as a stdio MCP server for native plugin distribution — the skill layer ports directly with no changes required.

- **2026-04-28:** Copilot CLI has a first-class plugin system: `copilot plugin install owner/repo`. Plugins require a `plugin.json` manifest in `.plugin/`, `.github/plugin/`, `.claude-plugin/`, or repo root. Plugins support: agents, skills, hooks, mcpServers, lspServers, commands. Plugins do NOT support the extension SDK (`@github/copilot-sdk/extension` / `joinSession`). Plugins install globally to `~/.copilot/installed-plugins/`. Two default marketplaces exist: `copilot-plugins` and `awesome-copilot`. Plugin manifest search order: `.plugin/plugin.json` → `plugin.json` → `.github/plugin/plugin.json` → `.claude-plugin/plugin.json`.
- **2026-04-28:** Our current extension.mjs uses `joinSession` to register 5 tools and `onSessionStart` to sync scripts. To work as a plugin, we'd need to convert the tools to an MCP server (stdio) since the plugin system doesn't load extensions. The skill layer (`SKILL.md`) ports directly — plugins support skills natively.
- **2026-04-28:** Per-repo provisioning (config.json template, PEM key scaffolding, charter injection) cannot be handled by the plugin system alone — it only installs to the user's global `~/.copilot/` dir. `install.sh` or a tool/hook is still needed for repo-level setup.
- **2026-04-28 (extension-vs-plugin verdict):** Extensions and plugins are two distinct mechanisms in Copilot CLI. **Extensions** (`.github/extensions/` project-scoped, `~/.copilot/extensions/` user-scoped) use `@github/copilot-sdk/extension` + `joinSession()` — full Node.js processes with JSON-RPC, can register tools/hooks/events, stateful, hot-reloadable. No install command; files on disk. **Plugins** (`copilot plugin install`) use `plugin.json` manifests and support agents/skills/hooks/mcpServers/lspServers/commands — but NOT extensions. Plugins have native install/update/uninstall lifecycle but require MCP servers for custom tools (not the extension SDK). For squad-identity, the extension SDK is the right fit because: (a) our 5 tools + onSessionStart hook already work, (b) plugin conversion would require a full MCP rewrite for zero behavioral gain, (c) user-global extensions at `~/.copilot/extensions/` give us cross-repo coverage without plugins, (d) `install.sh --global` provides a one-liner. The "unicorn" option (plugin wrapping an extension) is not supported — `plugin.json` has no `extensions` field.
